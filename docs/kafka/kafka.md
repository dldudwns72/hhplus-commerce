# Kakfa 란?
- 대규모 실시간 데이터 스트리밍을 위한 분산 메세징 시스템
- 발행(Publish) - 구독(Subscribe) 모델을 기반으로 동작
- 클러스터 기반으로 동작하며, 노드를 추가함으로써 쉽게 확장할 수 있다
  - 3.X 이하는 ZooKeeper 를 통한 클러스터링, 이상은 KRaft 를 통한 클러스터링 구성 

## 카프카 구조 (Producer - Broker - Consumer)

### Producer
- 이벤트 발생 시 메시지를 브로커로 전달하는 서비스
  - Topic, Key, Value 로 구성된 메세지를 전달
- 메세지 전송은 비동기 적으로 처리되며, 콜백을 통한 결과 전달 가능

### Broker
- Producer 으로 부터 전달 받은 Key-Value 형태의 메세지를 받고, 이를 적절한 파티션(Partition)에 전달 하는 역할
- 받은 메세지를 **복제**하여 다른 브로커에 저장할 수 있는데, 이를 통하여 내구성을 높이고 브로커 장애 시 데이터 손실을 방지
  - 복제본은 리더 브로커와 팔로워 브로커로 구붇되며, 리더 브로커는 실제 읽기/쓰기 작업을 처리하고, 팔로워 브로커는 리더 브로커의 데이터를 복제하는 역할
- 메세지를 일정기간 동안 저장하는 기능도 존재하며, 설정한 보존 정책에 따라 보존 기간을 설정할 수 있으며, offset 기반으로 순차적으로 저장
- Consumer 가 Topic 을 구독하였을떄, 브로커가 파티션의 메세지를 읽어 Consumer 에게 제공한다.
- Kafka 는 Consumer 가 처리한 메세지의 Offset 을 추적하여, 다음 메세지를 읽을 떄 어디서 부터 시작할지 결정할 수 있다.
- 결론: 메시지를 분배하고, 저장하며, 고가용성과 내구성을 보장하는 역할을 담당함

#### Topic
- 메세지가 저장되는 카테고리 단위로서, N개의 파티션으로 구성되어 분산 저장됨
- Kafka 에서 생산되는 모든 메세지는 특정 토픽에 속하고, 토픽은 메세지의 흐름을 관리하는 역할

#### Partition
- Kafka 에서 데이터를 분산 저장하고 처리하는 기본적인 단위 
- 같은 파티션 내에서는 메시지의 순서가 보장되나, 각 파티션 간의 메시지 순서는 보장하지 않기에 순서 보장을 위해서는 같은 키를 가진 메세지를 같은 파티션에 저장해야한다.
- 하나의 파티션이 여러 브로커에 복제될 수 있으며, 장애 발생 시 데이터를 잃지 않고 대응할 수 있다
- 파티션의 개수가 많아지면 병렬 처리가 가능하여 처리 성능이 향상되나, 과한 파티션 설정은 성능 부하를 가져올 수 있다.
  - 파티션 개수가 많을 때 왜 성능 부하가 올 수 있을까?
    - 각 파티션 마다 메타 데이터가 존재하는데 이에 따른 리소스 사용 증가로 인한 부하 가능
    - 각 파티션에 대한 메모리 할당이 증가하면서 이에 따른 부하 가능

### Consumer
- Kafka 토픽에서 전송된 메세지를 읽는 처리하는 역할
- 메세지를 읽을 떄 offset 이라는 고유 번호를 기록하여 다음에 메세지를 읽을 위치를 추적하고, offset을 관리하여 메세지 중복처리 및 처리 상태를 관리할 수 있습니다.
- 컨슈머 그룹을 통하여 여러개의 컨슈머가 서로 협력하여 **병렬**로 데이터를 처리할 수 있다.

#### Consumer Group
- 컨슈머를 모아놓은 그룹으로서, 하나의 컨슈머 그룹 내에서는 같은 파티션을 여러 컨슈머가 겹치지 않게 처리합니다. 즉, 하나의 파티션에 대해 한 명의 컨슈머만 메시지를 읽고 처리합니다.
- 여러 컨슈머가 각기 다른 파티션을 처리하면서 메시지 처리를 병렬로 수행할 수 있습니다.
- 만약 하나의 컨슈머가 실패하면, 다른 컨슈머가 그 파티션을 처리할 수 있기 때문에 시스템의 가용성이 보장됩니다.
- 메시지 중복 처리를 방지하면서, 각 파티션의 메시지는 한 번만 처리됩니다.
- 별도로 생성되는것이 아니며 Consumer 에서 group.id 지정 시 자동으로 그룹이 생성됩니다.
